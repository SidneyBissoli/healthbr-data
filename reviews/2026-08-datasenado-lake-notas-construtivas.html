O alvo, convertido em seis regras de projeto

  • R1 — Toda resposta padrão do portal sai de asset estático. O backend serve a cauda longa, nunca o caminho feliz.
  • R2 — SQL arbitrário só executa no browser do usuário (DuckDB-WASM, dado público, compute do próprio usuário).
  • R3 — O servidor só executa consultas nomeadas: parametrizadas, versionadas, com allowlist.
  • R4 — Todo asset de release é imutável e cacheável para sempre (immutable, max-age=1y).
  • R5 — Só ponteiros são mutáveis: um current.json minúsculo por dataset, TTL 60s. Atualizar = trocar o ponteiro. CDN sem purge, por construção.
  • R6 — Cota, sessão e telemetria só existem onde há computação do Senado. Isso dissolve a contradição "sem login × cotas": as duas promessas são verdadeiras, em camadas diferentes.

Anatomia do lake

Layout: /{dataset}/releases/{ts}-r042/ (imutável: data/*.parquet, delta/ opcional, manifest.json, dcat.jsonld) + /{dataset}/current.json (ponteiro) + /catalog.json global. Publicação atômica: escrever release → validar → trocar o ponteiro; rollback é apontar de volta. O histórico é a lista de releases retidos, endereçáveis por URL — ?release=r041 reproduz a análise daquele momento: é o "link reproduzível" do material, de graça.

Parquet dimensionado para range + WASM: arquivos de 100–500 MB no detalhe e ≤ 10 MB nos agregados de visão; row groups de 8–32 MB comprimidos (a granularidade real do range request); ordenação pela coluna de filtro dominante (min/max de row group vira índice de graça); zstd; bloom filter nas colunas de igualdade de alta cardinalidade; particionamento em diretórios só pelas 1–2 dimensões mais filtradas — fragmentar demais multiplica requests.

Proveniência que viaja com o arquivo: chave datasenado no schema metadata de cada Parquet (dataset, release, fonte, hash, pipeline, commit, licença). Custa zero no pipeline e responde "de onde veio isto?" quando o arquivo já saiu do portal.

Retenção (a regra que a consequência precisa): todos os releases por 24 meses; depois, 1 por trimestre; correção de dado pessoal ou erro grave ⇒ tombstone auditável (manifesto fica, dado sai, motivo registrado). Datasets sensíveis: conforme RIPD.

Três camadas — o teto do WASM resolvido por desenho

CamadaConteúdoRegra
Tier AAgregados de visão, ≤ ~10 MB por asset — um Parquet pequeno por visualização default.Toda página default renderiza só com Tier A. Carrega em qualquer celular.
Tier BDetalhe curado, particionado para range + WASM.Drill-down e SQL local no browser, com envelope declarado e testado (ex.: varreduras até ~1–2 GB, desktop).
Tier CConsultas nomeadas no backend.O que não cabe em A nem B. Nunca o caminho feliz.

No pipeline R + targets, Tier A, manifestos, DCAT e catálogo são targets derivados no mesmo DAG dos dados — recomputam por hash de conteúdo, e a descoberta sai do mesmo lugar que o dado.

Backend serverless mínimo — um contrato, três serviços

1. Consultas nomeadas. POST /q/{query_id}, parâmetros validados por schema; cada consulta é SQL versionado no repositório com limites declarados. Resposta gravada content-addressed por (release_id, query_id, params_hash) e servida pela CDN como immutable: novo release ⇒ chave nova ⇒ invalidação por construção, nunca purge — "gerenciar caches" vira consequência do esquema de chaves. Rate limit por IP só nos misses. Se SQL livre no servidor for mesmo necessário: DuckDB read-only em container isolado com tetos duros — opção B; lançar sem, e deixar a demanda provar.

2. Privacidade embutida — o achado de LGPD, resolvido neste desenho

O achado central da revisão cética era: um asset estático não pode negar uma consulta, e microdado de survey é reidentificável por cruzamento. O backend que já está no plano para agregações intensas é o único lugar da arquitetura onde controle de divulgação é aplicável. Então: datasets administrativos e agregados → estático, irrestrito (a maioria do catálogo; nada muda). Datasets com microdado de pessoa natural → o estático publica só agregados pré-suprimidos; o acesso fino sai só por consulta nomeada com limiar mínimo de célula (k ≥ n) imposto no servidor. A pergunta deixa de ser "publicar ou não" e vira "por qual camada". A classificação (o que é sensível, qual k) continua vindo do RIPD com o encarregado — pré-requisito que nenhum arranjo técnico substitui.

3. Modelos do Senado. Endpoint streaming com tool-use restrito ao mesmo contrato de ferramentas do portal; nunca SQL livre (R3). Cotas e sessão moram aqui — e só aqui (R6): é o único ponto com custo marginal real. E campo aberto de survey é entrada não confiável: o assistente lê texto de milhares de respondentes, e um deles pode conter instrução plantada — dado a citar, nunca instrução a seguir.

Agentes: um contrato, dois transportes

Definir as ferramentas uma vez, como JSON Schema neutro (search_datasets, get_schema, list_releases, run_named_query, run_local_sql browser-only, get_citation). Transporte 1: WebMCP no portal, para os modelos do usuário — adaptador de ~100 linhas em document.modelContext; quando a spec mudar de novo, muda o adaptador, não o produto. Transporte 2: servidor MCP clássico, mesmo schema, para clientes fora do browser — custa pouco além do que o transporte 1 já obriga a especificar, e entrega o caso "agentes usam o lake" hoje. Modelo de segurança auditável em uma frase: SQL arbitrário só existe em run_local_sql, no WASM do usuário, sobre dado público.

O que continua precisando de dono

  1. RIPD / classificação LGPD antes do primeiro microdado de survey. O §Privacidade dá o mecanismo; a decisão é institucional.
  2. Posicionamento frente a dados.senado.leg.br, à API existente e ao PDA 2026–2028. Uma página; nenhuma stack resolve colisão de mandato.
  3. Acessibilidade eMAG/WCAG como critério de aceite do portal — obrigação legal; a MPA estática é o melhor ponto de partida possível.
  4. Runbook + segunda pessoa capaz de operar o pipeline.
  5. Política de retenção publicada — a consequência vira compromisso.

Medir sem login: frescor (origem → flip do ponteiro), confiabilidade (pipeline + p95 da CDN) e uso do backend. Análise 100% no browser é invisível ao servidor por construção — é o preço da privacidade que a própria arquitetura oferece. Dizer isso no material vale mais como argumento do que como lacuna.
